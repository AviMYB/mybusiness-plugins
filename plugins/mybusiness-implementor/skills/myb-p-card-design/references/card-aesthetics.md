# Card Aesthetics / אסתטיקה של כרטיס

The rulebook for how a card **looks**. `SKILL.md` gets fields onto the page; this file decides where each one goes and how the card reads. A card is finished only when it looks right **in every state its form rules can produce** — not just in the state you happened to build it in.

Platform facts behind the rules (measured, not assumed) live in the knowledge base — read them when a rule's "why" matters:

- `../../myb-p-kb/references/80-capability-matrix/02-known-limitations.md` §22 — the traps in one place.

## 1. The aesthetics pass

**Run it** on every new card, every redesign, and **every time a field, a section or a `hidden` form rule is added to an existing card** — a new hide rule can wreck a layout that was fine yesterday. Order when a rule is part of the job: **layout first, then the rule** (`myb-p-form-rules`), then the visual check — so nobody ever sees the holes.

**Inputs, before planning anything:**
1. `Get-Page-Content(pageName, minimal: true)` — the current rows/columns.
2. `Get-Page-Content(..., minimal: false)` — once: the heading audit (A16) needs it, the `tcH` **ids** of headings appear only here, and so does the current `cssCode`.
3. `Get-Form-Rules(pageId)` — **mandatory.** Every field with a `hidden` action is a *conditional field*; note each rule's **condition** (field + operator + value) — fields hidden by the same condition form one *condition group*.
4. `Get-Schema(className)` — when fields are added or placed. Its per-field `dictionary` label is the canonical label (A21). Fields in the schema but not on the page: report them; add them only if the task asks.
5. `Get-Page-Versions(pageId)` — note the newest `_id` as the restore point before the first write (`Set-Page-Version` with `overrideHTML: true` undoes HTML changes; CSS/JS are separate).

**Output:** a layout plan — rows × columns per section — plus the **state table** (section 9). Build from the plan, then run the final check.

**Scope:** the form in `_MPID0`. The top bar (`_MPID1`) is generated by the master — leave it alone. A card often has a mobile twin (`apps/<app>/Mobile-<Entity>`) with its own layout and its own form rules: say so, and offer to run the same pass there.

## 2. Section order & grid

**A1. One field per column; the row is the unit.** Place exactly one field in each column of a field row. Do not stack fields inside one column.
*Why:* built-in cards do it this way, visual rows stay aligned, and a stacked column breaks the moment one of its fields is hidden — the fields below move up and fall out of line with the neighbouring columns.

**A2. Fill full-first, right-to-left; the remainder last.** Within each group of a section (A3a): N fields on a K-column grid → `ceil(N/K)` rows, every row full except the last; the remainder sits in the **last** row starting at **column 0** (the right side in RTL), trailing columns empty.
- 5 fields on `[4,4,4]` → `3 + 2` (never `2 + 3`). 7 → `3 + 3 + 1`. 8 → `3 + 3 + 2`.
- The last row keeps the section's grid — two remaining fields stay in `[4,4,4]` (columns 0 and 1), **not** stretched to `[6,6]`. Column edges line up down the section.
- A lone remainder (N = 4, 7, 10 on three columns) is legal but weak. Remedies in order: move a field in from a neighbouring section **where it belongs topically**; or a grid that divides N (4 → `[6,6]` as `2 + 2`, or `[3,3,3,3]` when all four are compact); otherwise accept `3 + 1`. **Topic beats balance** — never move a field out of its subject to even up the rows. Never put the short row first.

**A3. One grid per section, a fixed group order inside it.** Choose the section's column count once (`[4,4,4]` default; `[6,6]` for long inputs or a section of 2/4 fields; `[3,3,3,3]` for compact fields only). When choosing between two legal grids, take the card's dominant grid — column edges then line up across sections too. Only full-width `[12]` rows may differ.

**A3a. Group order inside a section** — A2 applies inside each group:
1. always-visible input fields (identity first: name, record number, status, type …);
2. the conditional fields, continuing the same flow (section 3);
3. checkbox row(s) (A9) — except a checkbox that **controls** conditional fields, which comes right before them (Example 5);
4. working metadata (A11);
5. long text, full width — the last row of the form part of the card (A10).

## 3. Conditional fields

A `hidden` form rule hides only the field's `.form-group`; the column stays, full width (KB 30/07 §8). So the position of a conditional field decides whether hiding it leaves a **hole** or just a **shorter row**:

| Hidden field sits in… | Result |
|---|---|
| column 0 or a middle column, with visible fields after it in the row | a hole inside the row — **the defect** |
| after every visible field of its row | the row ends early — looks normal |
| a row where **all** fields hide under the same condition | the row disappears (≈21px residual on a ticket card, 1px on a `NewMaster` card) |
| a stacked column | the column falls out of line — **the defect** |

**A4. Conditional fields continue the flow.** Lay out the section's always-visible fields first (A2), then the fields of a condition group **directly after them in the same reading order** — they may fill the trailing columns of the last always-visible row and run on into new rows. Hidden, the section simply ends earlier: no hole, rows still full-first. Visible, the flow is still full-first.
- 7 visible + 2 conditional on `[4,4,4]`: `V V V / V V V / V C C` → visible state `3 + 3 + 3`, hidden state `3 + 3 + 1`.
- A conditional field never comes **before** an always-visible field in the flow.
- **Only one condition group may share a row with visible fields** — the first one. Each further group starts on a new row (otherwise hiding the earlier group opens a hole in front of the later one).

**A5. Never scatter conditional fields over several rows' last columns.** `V V C / V V C / V V V` has no holes, but its hidden state reads `2 + 2 + 3` — short rows above a full one. Keep a group together, after the visible fields (A4).

**A6. Where the group lands, and the controlling field.** Conditional fields sit at the end of their section's input flow (A3a). To keep them close to the field that controls them, put the **controlling field in the section's last always-visible row** — the user flips it and the new fields appear right after it. A checkbox that controls fields comes right before them (A3a item 3). Checkbox rows, metadata and the trailing long-text row are separate groups and do not count as "visible rows after" the conditional fields. Never give conditional fields a section heading of their own — form rules hide fields, not headings, so the heading would stay behind alone. The controlling field itself is never hidden.

**A7. Check both states of every condition.** A2 applies to each state separately, group by group: the always-visible flow alone (hidden state) and the flow with the group (visible state) must both be full-first with no hole. Write the state table (section 9) before building.

**A8. Mutually exclusive groups** (never visible together — lead-only vs. customer-only fields) each start their own row; adjacent rows are fine — one of them is always gone. Never let two such groups share a row: whichever is hidden leaves a hole.

*Built-in precedent:* the Account card hides `TypeId`/`StatusId`/`OwnerId` together while the record is a lead (one whole row), keeps `LeadStatusId`/`LeadSourceId`/`LeadOwnerId` in another row, and gives `LeadConversionDate` a row of its own.

## 4. Field-type rhythm

**A9. Checkboxes in their own row.** A Boolean renders as a label plus a small box — shorter than an input, so it makes a mixed row uneven. A section's checkboxes share their own row(s) (`[4,4,4]` or `[3,3,3,3]`), filled per A2 (built-in precedent: Account `dontSendEmail`/`dontSendSms`/`dontSendWhatsApp`). A single checkbox may sit alone in its row; if it topically belongs with another section's checkboxes, move it there instead. **One caption per checkbox:** `add-new-field` renders a Boolean's caption twice (outer label + beside the box) — rewrite its `.form-group` with the built-in checkbox markup, outer label empty and hidden (SKILL.md gotcha 34).

**A10. Long text spans the width, at the end, as stored markup.** Free text (Comment, Description, Notes, or any long-text field) takes a `[12]` row of its own as the **last row of the form part** of the card, after the structured fields. It needs no heading of its own — a heading saying "הערות" over a field labelled "הערות" is repetition (A20). **It must be a real `<textarea>`:** `add-new-field` stores every String as a single-line input, `Comment` included; store textarea markup with `set-html-content` on the field's `.form-group` (SKILL.md, "Long-text fields"). A short field (phone, date, amount) is never full width.

**A11. Working metadata after the working fields.** Read-only working data — source, conversion date, created-by user when the customer wants it shown — goes together after the working fields of its section, before the long text. Identifiers are **not** metadata: the record number belongs with identity, first (built-in Case card). Platform columns `createdAt`, `updatedAt`, `objectId`, `ACL` are not placed on cards — built-in cards don't, and they are not user-editable.

## 5. Headings

**A12. Section heading = H2 with class `TicketHeadline`, plain text.** Exactly the element the built-in cards use. Create it in two calls (the MCP tool alone emits a bare `<h2>`, which on a ticket card renders larger and bolder than the built-in headings next to it):
```
1. Add-Edit-Text-Element(pageId, elemType: "H2", html: "פרטי התקשרות", rowId: <[12] row>, columnNumber: 0)
   → "text element with id P286 added"
2. Edit-Page(pageId, actions: [{ actionType: "set-html-content", intoExistingElemId: "P286",
     htmlContent: "<div class=\"textContainer H2\"><h2 class=\"TicketHeadline\">פרטי התקשרות</h2></div>" }])
```
On a `NewMaster` card (every `Create-Form-Page` card) the class changes nothing visible today — keep it anyway: one markup everywhere, and the card renders right if it ever moves to the ticket shell. The **title row** `Create-Form-Page` creates is a bare `<h2>` too: make it the first section's heading (rename + class) — built-in cards open with a section heading, not a page title.

**A13. No inline styling in a heading — ever.** No `<font>`, `<span style>`, `<b>`, `color`, `face`, `font-size`. Measured: the master's colour wins over `<font color>`, but an inline `font-size` survives, and a `<span style="font-family:…; color:…">` wins outright (Arial, orange on a navy card).

**A14. Sub-headings = H3, sparingly.** Prefer splitting a section in two over sub-headings. When one is needed (a labelled group inside a section), use H3 with plain text — markup `<div class="textContainer H3"><h3>text</h3></div>`. On a ticket card the master renders H3 *heavier* than the section heading; the standard CSS block puts it below on both masters. Existing sub-headings: keep them unless the group is really a section of its own. Never H1 or H4 on a card.

**A15. One look across the card — and across cards.** Do not restyle headings per page (no page-level size/colour overrides). The platform itself styles ticket cards (18px/400) and `NewMaster` cards (24px/600) differently — that difference is the platform's, not yours to patch. If a customer's brand truly requires a different heading colour, set it once, as a class-level rule for every heading on the card — never on an individual heading.

**A16. Heading audit (every redesign).** In the `minimal: false` read, list every `<h1>`–`<h4>` in the form — **including related-table headers**, which `Add-Table-View-to-Form-Page` creates as a bare `<h2>` inside the table element — and fix each one that: is an `h2` without `TicketHeadline`; carries `<font>`, `style=`, `<b>`/`<strong>`, `<span>`; is an `h1`/`h4`; ends with a colon. Both fixes are verified; pick by convenience:
- **`set-html-content`** on the heading's `tcH` id with the full markup (`<div class="textContainer H2"><h2 class="TicketHeadline">text</h2></div>`, or the H3 markup for a sub-heading) — works for every case, and several fixes batch into **one** `Edit-Page` call.
- **`Add-Edit-Text-Element(elemId, elemType, html: "<plain text>")`** — keeps the element's class and replaces everything inside it; good for one heading that already has the right class. After an H1 was rewritten to H2 markup, edit it with `elemType: "H2"`.

A **stray or duplicate heading**: if it sits alone in its row, `delete-row` that row (removes the heading — verified); if it shares a column with another heading, move it to a row of its own with `move-existing-object` and reuse or delete it there. `Duplicate-Element` is not a shortcut for new headings — the copy lands in the same column as the original.

Heading text: short noun phrase, specific ("פרטי התקשרות"), no trailing colon. "פרטים נוספים" is too vague — built-in cards use it; don't copy them on this point.

## 6. Soft separation & whitespace

**A17. Separate sections with the hairline, not with clutter.** The standard CSS block draws a light line (`var(--border-color)`, #E8E8E8) with a little air above every section-heading row and every related-table block, except the first row of its container. That is the separation — no separator elements, no coloured bars, no boxed sections. Free text at the end of the form gets no line of its own (A10) — like built-in cards.

**A18. No stray empty space.** No empty rows inside or between sections. When you apply the CSS block, delete empty spacer rows that sit directly above a heading row — the hairline replaces them (built-in cards use spacer rows; on a built-in card leave the ones in areas you are not touching). No row whose columns are all empty. Empty columns only as the trailing columns of a group's last row (A2, A4). Delete — or reuse as a move target (section 10) — the rows a re-layout empties, in **one** step after the moves, after a re-read.

**A19. One transition before related tables.** Between the last form section and the related-record tables: exactly one transition — the hairline above the first table block. No extra empty rows.

## 7. Labels & consistency

**A20. Short labels, no colon, no repetition** — for labels you write: one to three words, no trailing colon, do not repeat the section's subject in every label ("טלפון" inside "פרטי איש קשר").

**A21. Same field, same label, everywhere — and A21 beats A20 for existing fields.** A field keeps its canonical label: the `Get-Schema` per-field `dictionary` entry, which is also what the list page shows. Strip working notes left in labels ("(מותנה)", "(חדש)"). When terms change, see `myb-p-rename-terms`.

**A22. Same section order across sibling cards.** Cards of related entities (Account / Contact / Lead) share the section order: identity → contact → address → business → metadata → free text → related tables.

## 8. The standard aesthetics CSS block

Apply on every card you build, redesign, or re-lay out, through `Edit-Page-CSS-JS(cssCode)`. **Merge, never overwrite:** read the current `cssCode` (`minimal: false`), drop any previous copy of the block (between the marker comments — including a `v1` copy), drop the retired heading rule (below), append this block, write the result.

```css
/* >>> card-aesthetics v2 */
.dbForm :is(h1,h2,h3,h4) :is(font,span,b,strong) { color: inherit !important; font-family: inherit !important; font-size: inherit !important; font-weight: inherit !important; }
.dbForm h3 { font-size: 15px !important; font-weight: 400 !important; margin: 10px 0 2px !important; }
.dbForm .rDivider:not(:first-child):is(:has(> .sDivider > .tcH h2), :has(> .rDivider > .sDivider > .simbla-table)) { border-top: 1px solid var(--border-color, #E8E8E8); margin-top: 12px; padding-top: 6px; }
/* <<< card-aesthetics v2 */
```

**This block is the only page CSS the pass writes, and the aesthetics pass never writes JS.** Everything else in this rulebook is native: page structure, stored markup, form rules.

Line 1 — heading uniformity guard (inline wrappers inherit the heading's class style). Line 2 — sub-heading below the section heading. Line 3 — the soft hairline above section headings and related-table blocks. All measured in the browser on both masters (KB 30/03 §4).

**Retired — remove the whole rule when you meet it:** `.TicketHeadline { font-size: 24px !important; font-weight: 800 !important; margin-top: 17px !important; padding-bottom: 7px; }` (its spacing goes too — the hairline line takes over), and headings built from `<font color="#3249b3" style="font-size: 24px;">`.

**Cross-card consistency:** the hairline changes how a card looks next to its siblings. After applying the block to one card of a tenant, offer to apply it to the sibling cards (Account / Contact / Sale / Case / Task) so the system keeps one look — don't do it unasked.

## 9. The state table & the final check

**The state table** — one line per form-rule condition that hides fields, written into the plan before building:

| Condition | Fields hidden | Rows affected | Layout in hidden state | Layout in visible state |
|---|---|---|---|---|
| `IsVip ≠ checked` | VipLevel, VipSince | R5 (own row, after the IsVip row) | R5 gone; input flow 2, checkbox row 1 | R5 = 2 fields from column 0 |

Every "Layout" cell must pass A2 per group (A3a): full rows first, remainder last, no hole. With no `hidden` rules the table has one line: "single state".

**The final check** — after building, before reporting done:
1. Re-read `minimal: true`: one field per column (A1); per-group fill order (A2, A3a); conditional fields per A4–A8; checkboxes / long text / metadata per A9–A11; no empty rows (A18).
2. Re-read `minimal: false`: every section heading is `h2.TicketHeadline` with plain text, related-table headers included (A12–A16); long text is a `<textarea>` (A10); the CSS block is present exactly once, the retired rule is gone.
3. **Look at it.** Open the card in a browser and capture it in **each** state of the state table — toggle the controlling field without saving — at full width and at sidebar width. Read the computed style of every heading (they must match per level). "Exists" is not "visible": a `success: true` and a correct YAML prove nothing about the look. A `NewMaster` card opened by direct URL shows an empty record — enough for the client-side state toggles; to see a saved record, open it from its list page (sidebar). If no browser is available, say so explicitly and present the state table plus the **expected** computed style per heading as the evidence — never report a visual result you did not see.

## 10. Re-layout mechanics

Moving fields around an existing card has three measured traps (KB 30/03 §3 rules 10–14):

- **Moving into an occupied column stacks** — no error; the field lands under the existing one and breaks A1. Order every batch so each target column is emptied **earlier in the same batch** ("vacate, then fill"), or use an empty staging row.
- **`edit-row` to fewer columns drops fields** — `[4,4,4]` → `[6,6]` with a field in column 2: success, and that field is gone from the page (still in the schema; re-add it). Before narrowing, move the fields out of the columns that will disappear. Widening keeps every field.
- **Re-read between dependent steps** — after a batch of moves, `Get-Page-Content(minimal: true)` before any `delete-row` (deleting a populated row loses its fields).

Useful moves: an existing empty row can be re-gridded with `edit-row` and used as a move target — fewer calls, real ids. `move-existing-field` needs only `fieldName` + the target position. `move-existing-object` moves non-field elements (headings, empty rows) — never a row that still holds fields.

## 11. Worked examples

RTL note: column 0 is the right-hand cell; the diagrams list columns 0 → 2 left to right for readability. V = always visible, C = conditional.

### Example 1 — two conditional fields scattered across a 3 × 3 grid

A section of 9 fields on `[4,4,4]`. A rule hides `CancelReason` (row 1, middle) and `CancelDate` (row 2, first column) while `Status ≠ בוטל`.

```
BEFORE (Status = פעיל)                 AFTER (A4: visible first, the group continues the flow)
row 1: Name | ░░░░░░ | Status           row 1: Name  | Status | Type
row 2: ░░░░░░ | Type | Owner            row 2: Owner | Phone  | Email
row 3: Phone | Email | Date             row 3: Date  | CancelReason | CancelDate
```
Hidden state: `3 + 3 + 1` (row 3 ends after Date). Visible state: `3 + 3 + 3`. Status stays in row 1 because identity comes first (A3a); with a three-row section the revealed fields are still in view. In a long section, prefer moving the controlling field down to the last always-visible row (A6) when the topic order allows it.

Rejected alternatives: the group in a row of its own (`3 + 3 + 1 + 2` visible — a short row above a short row, worse than A4); each conditional field in the last column of its row (`2 + 2 + 3` hidden — A5).

### Example 2 — five fields on a three-column grid
`[4,4,4]`: row 1 = fields 1–3, row 2 = fields 4–5 in columns 0–1, column 2 empty. Never fields 1–2 on top and 3–5 below; never row 2 stretched to `[6,6]`.

### Example 3 — one conditional field in a small section
Section: Name, Status, Owner, Amount (always) + ReasonForLost (hidden unless Status = נכשל). Flow on `[4,4,4]`: row 1 = Name | Owner | Amount, row 2 = Status | ReasonForLost. Hidden: `3 + 1`; visible: `3 + 2`; Status (the controlling field) sits right before the field it reveals (A6).

### Example 4 — heading audit on an existing card
Found: `<h2 class="TicketHeadline">פרטי לקוח</h2>` (ok), `<h2>כתובת</h2>` (no class), `<h2 class="TicketHeadline"><font color="#3249b3" style="font-size: 24px;">פרטי עסק</font></h2>` (inline styling), `<h3><b>הערות פנימיות</b></h3>` (inline bold), the related table's `<h2>אנשי קשר</h2>` (no class). Fix all four in **one** `Edit-Page` call of `set-html-content` actions on their `tcH` ids (H2 markup for the three headings, H3 markup for the sub-heading), then merge the CSS block.

### Example 5 — a checkbox that reveals fields (the most common shape)
Section "מידע עסקי": Source, Amount (always), IsVip (checkbox, always), VipLevel + VipSince (hidden unless IsVip is checked), Comment (long text).
```
row 1: Source | Amount |            ← input flow (A2)
row 2: IsVip  |        |            ← the controlling checkbox, alone (A9), right before its fields (A3a, A6)
row 3: VipLevel | VipSince |        ← condition group, own row because a checkbox row precedes it (A9 forbids mixing)
row 4: Comment ———————————————      ← long text [12], last, stored <textarea> (A10)
```
State table: hidden → rows 1, 2, 4 (row 3 gone, 1px on `NewMaster`); visible → row 3 shows 2 fields from column 0. Each group is full-first; no hole in either state. (Measured live on the playground lab card.)
